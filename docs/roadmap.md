# 四阶段内核演进路线图

目标：用「加功能」逼出「内核」。

每一阶段都实现同一个「本地知识库问答」，但换一个 Agent 框架作为内核。
新增的功能不是随意加的，而是顺着那个框架最核心的设计去选。

---

## Stage 1 · LangGraph —— 把流程画成「图」

**内核设计**：StateGraph、共享状态、显式节点与边。

**新增功能**：基础 RAG（建索引 → 检索 → 生成）。

**要回答的问题**：为什么 LangGraph 把 RAG 建模成一张图，而不是一段顺序代码？
答案在于：图里的每个节点是独立可替换的单元，状态是唯一的数据通道，
之后加「重写问题」「多路召回」「重排序」，都只是往图里插节点，不用推翻重写。

---

## Stage 2 · DeerFlow —— 把流程画成「规划-执行循环」

**内核设计**：Agent Harness、工具注册、规划与执行分离。

**新增功能**：多步问答。用户问一个复杂问题，先拆成多个子问题，分步检索、逐步作答。

**要回答的问题**：什么时候「图」不如「循环」？
当问题需要动态决定下一步（拆不拆、拆几个）时，DeerFlow 的规划-执行循环比固定的图更自然。

---

## Stage 3 · DeepSeek Super-Agent —— 把「写索引」变成「可靠副作用」

**内核设计**：Effects 队列、Transactional Outbox、幂等投递。

**新增功能**：可靠副作用。索引写入「先记账、后动手」，保证不丢、不重。
呼应 dsh-superagent 里 `effects.ts` 的 `ON CONFLICT DO UPDATE` 与 `generation` 防覆盖。

**要回答的问题**：RAG 的「建索引」其实是一次有副作用的写操作，
如何借用事务性 Outbox 的思想，让它在中途崩溃时也能保证一致性？

---

## Stage 4 · Codex —— 把「模型」和「执行」都变成可插拔

**内核设计**：模型路由、执行沙箱。

**新增功能**：多模型切换、可插拔后端。
同一个问答，可以在本地模型 / 云端模型 / 自定义后端之间切换。

**要回答的问题**：当模型能力趋同，内核的护城河从「选哪个模型」转移到「怎么把模型接进来」。
Codex 的模型路由和执行沙箱，是怎么做这种抽象的？

---

## 贯穿始终的一条主线

每一阶段的「内核」，都会被单独写进对应的公众号源码分析系列：
- Stage 1 ↔ LangGraph 系列（Graph 编译 / Channel 状态 / Checkpointer）
- Stage 2 ↔ DeerFlow 系列（规划-执行 / 工具绑定）
- Stage 3 ↔ dsh-superagent 系列（Effects 队列 / Outbox 幂等 / 订阅扇出）
- Stage 4 ↔ Codex 系列（模型路由 / 沙箱）

工具是「果」，内核是「因」。读者既能 clone 下来跑，也能顺着文章看懂每个内核为什么这么设计。
